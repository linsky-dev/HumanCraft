# Contributing

A useful contribution demonstrates a real user problem, states when the proposed rule applies and when it does not, and supplies an observable acceptance check. Prefer small changes over expanding the skill indiscriminately.

- For an interaction bug: provide a minimal anonymized reproduction, expected outcome, actual outcome, severity, and regression test. Do not submit proprietary screenshots, real customer data, credentials or book extracts.
- For a new skill rule: show which failure it addresses, alternatives and tradeoffs, and a case where it must not activate. Keep the entry lean and put specialized guidance in a reference file.
- For an independent evaluation: preregister tasks and comparisons; freeze versions, budgets and the oracle; keep hidden cases out of public training examples; report all results and missing evidence. Distinguish self-application, independent agents and actual humans.
- Run the validation and unit tests. If relevant, run the browser calibration. Do not change assertions to match a patch; explain any legitimate changes to the contract. Never submit synthetic participants as human observations.

Maintainers should review both engineering and human impact. No artificial reviews, stars or fabricated evidence.
