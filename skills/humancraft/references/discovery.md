# Discovery: solve the right problem

**Trigger:** new product, feature, unclear request, redesign or recurring user complaint.

Start with activity rather than features. Identify actors, their real outcome, trigger, environment, current workaround, data they trust, handoffs, and conditions for completion. Separate user need from proposed implementation. An operator asking for a new button may really need faster access to an existing operation.

For larger tasks use divergent problem discovery, convergent problem definition, alternative concepts, then small prototypes and tests. Evidence may come from observations, support logs, task completion recordings, interviews and accessibility feedback. Do not generalize from an invented persona; if unavailable, mark hypotheses and propose research.

Produce: outcome statement (actor + task + context + desired result), current journey, friction/causal hypothesis, constraints, two plausible options, chosen option with reasoning, success metrics and a prototype/test plan. Use qualitative findings and time/errors/completion metrics as appropriate. Keep technical and business constraints explicit; stage incremental improvements when a disruptive model would require risky migration or relearning.

Decision test: if a feature does not support an identified outcome, defer it unless it is a requirement. If user requests conflict, name the tradeoff instead of silently optimizing for one group. Preserve user choice, legal and safety constraints, and avoid engagement metrics that reward harm.
